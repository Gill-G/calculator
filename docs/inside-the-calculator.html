The map: three programs, two ports

What is actually running when you open the page

When you ran ./start.sh, you did not start "the calculator". You started three separate programs that cooperate. Nothing in software makes you do it this way — someone decided to split the work, and the split is the first thing worth understanding.

A server is just a program that starts up and then waits. It does nothing until a message arrives, answers it, and goes back to waiting. It never finishes, which is why your terminal appears to hang after you start one — that is the program doing its job.

A client is whatever sends those messages. Here the client is your web browser. Browsers are enormous programs whose main skill is asking for files over a network and drawing whatever comes back.

Because two servers are running on one machine, they need a way to be told apart. That is a port — a numbered door on your computer. Python holds door 8000, Node holds door 3001. 127.0.0.1 (also spelled localhost) means "this same machine", so http://127.0.0.1:8000 reads as door 8000, right here.

Notice what this buys: the two servers know nothing about each other. Kill the Node one and the calculator still adds up — only the facts bubble notices, and it says so. That is loose coupling, and it is the whole reason to split a program into pieces.

start.shrunning both at once
node facts-server.js &          # & = run it in the background
NODE_PID=$!                     # remember its process number
trap 'kill $NODE_PID' EXIT INT TERM   # kill it when we exit

python3 server.py               # this one holds the terminal

A shell script is a list of terminal commands in a file. This one starts Node in the background, notes its process id, and sets a trap — a promise to run kill whenever the script ends. Without that trap, Ctrl+C would stop Python and leave Node running invisibly, still holding port 3001.

One keypress, end to end

Following 7 × 8 = through all three programs

This is the single most useful thing to hold in your head. Everything else in the codebase is a detail hanging off one of these six stages.

Stage 3 is worth pausing on. The keypad shows × and ÷ because those are the symbols people read; Python only understands * and /. So the code keeps a lookup table — a plain object mapping each display symbol to its Python spelling — and swaps them one character at a time on the way out.

static/app.jsxlines 5–12, 269–274
const TO_PYTHON = {
  "×": "*", "÷": "/", "−": "-", "^": "**", "√": "sqrt", "π": "pi",
};

function toPython(display, symbols) {
  return display
    .split("")                        // "7×8" → ["7", "×", "8"]
    .map((ch) => symbols[ch] || ch)   // swap it, or keep it as-is
    .join("");                        // back into one string → "7*8"
}

split, map and join are the three verbs you will see over and over in JavaScript: take a list apart, do something to every item, put it back together. symbols[ch] || ch reads as "the replacement if there is one, otherwise the character unchanged" — || here is not really "or", it is "fall back to".

The browser half: React

988 lines of app.jsx, and the one idea underneath them

The old way to build a web page was to describe changes: find the display element, change its text, now disable that button. Every change was an instruction, and you had to keep track of which instructions had already run.

React replaces that with one rule: you describe what the screen should look like for a given set of facts, and React works out the changes for you. The facts are called state. Change the state and React re-runs your description, compares it against what is on screen, and edits only the parts that differ.

Componentsa function that returns a piece of screen

A React app is built from functions that return markup. app.jsx defines nine of them — Display, History, ThemeMenu, FactBubble and so on — plus Calculator, which assembles the rest. Values passed into a component are called props, and they only ever flow downward: a parent tells a child what to show, never the reverse.

static/app.jsxlines 521–532 · a small component in full
function AnswerChip({ value, onInsert }) {     // ← two props
  return (
    <button className="answer" onClick={onInsert}
            title={`Insert the last answer (${value})`}>
      <span className="answer__label">ANS</span>
      <span className="answer__value">{value}</span>
    </button>
  );
}

That HTML-looking syntax inside a JavaScript function is JSX. Browsers cannot read it, so something must translate it into ordinary JavaScript first. Most projects do that translation ahead of time with a build step. This one skips the build entirely: index.html loads Babel from a CDN and translates app.jsx in the browser, every page load. Slower, but it means there is nothing to install and nothing to recompile after an edit.

The curly braces are the escape hatch back into JavaScript: {value} means "put the value of this variable here". onClick={onInsert} hands the button a function to call later — the function itself, not its result, which is why there are no parentheses after it.

State and hooksthe facts a component remembers between renders

A component function runs from scratch on every render, so ordinary variables inside it are forgotten each time. useState is how a value survives. It is one of React's hooks — functions whose names start with use that plug a component into React's machinery.

static/app.jsxlines 647–662 · everything the calculator remembers
const [expression, setExpression] = useState("");   // what's on the display
const [hint, setHint]       = useState("");         // the small line above it
const [error, setError]     = useState("");         // a problem to show
const [pending, setPending] = useState(false);      // waiting on the server?
const [settled, setSettled] = useState(false);      // showing a finished result
const [answer, setAnswer]   = useState("");         // last result, in decimal
const [history, setHistory] = useState([]);         // the last 25 sums
const [theme, setTheme]     = useState(readStoredTheme);
const [mode, setMode]       = useState(() => readStored(MODE_KEY, MODES, "standard"));

Each line hands back a pair: the current value, and the only function allowed to change it. const [a, b] = ... is destructuring — pulling two items out of a returned array in one line. The names are yours to choose; setX is convention, not a rule.

Read that list as a specification. Those nine facts, plus a handful of settings, are the calculator. Everything on screen is derived from them.

Effectswork that has to happen outside the render

Rendering is supposed to be pure description. Saving to disk, listening for keystrokes, calling a server — that all has to happen somewhere else, and useEffect is that somewhere. It takes a function and a list of values to watch; when one of those values changes, the function runs again.

static/app.jsxlines 701–708
useEffect(() => {
  document.documentElement.setAttribute("data-theme", theme);
  try {
    localStorage.setItem(STORAGE_KEY, theme);
  } catch (err) {
    /* the theme still applies for this session */
  }
}, [theme]);          // ← re-run this only when `theme` changes

The keyboard listener (lines 885–916) uses the same tool with an important addition: it returns a function. React calls that returned function to clean up before re-running the effect, so the old listener is removed before a new one is added. Forgetting that is one of the classic memory leaks in React code.

Data-driven interfacesdescribe the buttons, don't write them out

The three keypads hold 24, 40 and 32 buttons. None of them is written out as markup. Each keypad is an array of plain objects, and one loop turns any of those arrays into buttons.

{keys.map((key) => (

Accessibility attributes like this appear throughout the file — role="tablist", aria-pressed, aria-modal — and they cost almost nothing to write while the component is being written.

A rule you can carry anywhere: when you find yourself writing nearly-identical code a fourth time, the repetition is data in disguise. Pull the differences into a list, and write the shared part once.

The wire: HTTP and JSON

How two programs that share no memory manage to talk

The browser and Python are separate programs. They share no variables. Everything one tells the other has to be flattened into text, sent down a socket, and rebuilt on the far side. Two conventions make that bearable.

HTTP is the request-and-answer format. A request names a method (GET to fetch something, POST to send something), a path (/api/calc), some headers (notes about the message), and optionally a body. The answer carries a status code: 200 means fine, 400 means "your request was wrong", 404 means "no such thing here", 500 means the server broke.

JSON is the way values are written down as text. Objects, arrays, strings, numbers, true/false/null. Both languages can turn their native values into JSON and back, which is why a Python dictionary can arrive in JavaScript as an object without either side knowing the other exists.

static/app.jsxlines 784–831, abridged · the browser's side of the conversation
setPending(true);                       // dim the display while we wait
try {
  const response = await fetch("/api/calc", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({              // JS object → text
      expression: toPython(resolved, activeMode.symbols || TO_PYTHON),
      mode, angle, base, width: Number(width),
    }),
  });
  const data = await response.json();   // text → JS object

  if (!response.ok) {                   // a 400 still "arrived" successfully
    setError(data.error || "Could not calculate that");
    return;
  }
  setExpression(data.result);
} catch (err) {
  setError("Cannot reach the server");  // no reply at all
} finally {
  setPending(false);                    // runs either way
}

Asynchronywork that finishes later, without freezing everything else

A network round trip takes milliseconds at best and forever at worst. If the browser simply waited, the whole page would lock up. So fetch returns immediately with a promise — a placeholder for a value that has not arrived yet.

await means "pause this function here until the promise resolves, and let everything else carry on". It is a marker of a function declared async. This is why the code reads top-to-bottom like ordinary sequential logic while behaving nothing like it.

The three-way split matters. try holds the hopeful path. catch catches the case where no answer came back at all — server down, network gone. And finally runs no matter which of those happened, which is the only safe place to clear pending; put it in try and a failed request leaves the display dimmed forever.

Note that a 400 response does not reach catch. The message arrived perfectly — it just says no. That distinction, between "the conversation failed" and "the answer was no", trips up nearly everyone once.

Same origin, and why the facts service needs CORS

The calculator posts to /api/calc with no host in front of it, because the page itself came from port 8000 — same origin, so the browser allows it without ceremony.

The facts service is on port 3001. Different port means different origin, and browsers block those requests by default to stop a malicious page from quietly reading another site's data. The fix is that the receiving server must say it does not mind. That is what one line of facts-server.js does.

facts-server.jslines 33–46 · an entire web service
const app = express();
app.use(cors());     // "any origin may call me" — this is the permission

app.get("/api/fact", (req, res) => {
  const index = Math.floor(Math.random() * FACTS.length);
  res.json({ fact: FACTS[index], index, total: FACTS.length });
});

app.listen(PORT, "127.0.0.1", () => { … });

Express is a framework: a library that supplies the boring parts of being a web server so you only write the interesting parts. app.get(path, handler) registers a function to run when that path is requested; req is the incoming request, res is the reply you are building. Along with cors, these are the only two pieces of third-party code in the entire project.

The Python half: parsing, not guessing

Turning the string "2 + 3 * 4" into the number 14

Here is the honest problem. Python hands you "2 + 3 * 4": nine characters. It is not maths yet. It is text that happens to look like maths, and something has to work out that the multiplication binds tighter than the addition.

Python ships with a function that would do the whole job in one line: eval("2 + 3 * 4") returns 14. It is also the single most dangerous function in the language, because it will run anything. __import__("os").system("rm -rf ~") is a perfectly valid expression. On a server that accepts strings from strangers, eval hands them your machine.

So this codebase does something better. It uses Python's parser to turn the text into a structure, and then walks that structure itself — deciding, node by node, whether each thing is allowed.

server.pylines 125–130
try:
    tree = ast.parse(expression, mode="eval")   # text → structure
except SyntaxError:
    raise CalculationError("Invalid expression")

value = _eval_node(tree.body, functions)        # structure → number

An AST — abstract syntax tree — is what a parser produces: the same expression, arranged so its structure is explicit. Precedence stops being a rule to remember and becomes a shape. The multiplication is lower down the tree, so it necessarily happens first.

Recursiona function that solves a problem by calling itself on a smaller piece

_eval_node is 45 lines long and evaluates expressions of any depth, because it never tries to handle a whole expression. It handles one node, and asks itself for the rest.

server.pylines 139–184, abridged · the heart of the whole program
def _eval_node(node, functions):
    if isinstance(node, ast.Constant):              # ← the base case
        if isinstance(node.value, bool) or not isinstance(node.value, (int, float)):
            raise CalculationError("Only numbers are allowed")
        return node.value                           # a leaf: answer directly

    if isinstance(node, ast.BinOp):                 # ← the recursive case
        op = BIN_OPS.get(type(node.op))
        if op is None:
            raise CalculationError("Unsupported operator")
        left = _eval_node(node.left, functions)     # ask myself about the left
        right = _eval_node(node.right, functions)   # …and the right
        if op is operator.pow and abs(right) > MAX_EXPONENT:
            raise CalculationError(f"Exponent must be within +/-{MAX_EXPONENT}")
        try:
            return op(left, right)                  # now combine the answers
        except ZeroDivisionError:
            raise CalculationError("Cannot divide by zero")

    # …UnaryOp, Name and Call branches follow the same shape…

    raise CalculationError("Invalid expression")    # ← anything else: refused

Every recursive function needs two things, and both are visible here. A base case that returns without recursing — a Constant is just a number, so it answers immediately. And a recursive case that calls itself on something strictly smaller — the children of a node are always closer to the leaves than the node itself. Together they guarantee the process ends.

Dispatch tablesa dictionary standing in for a wall of if-statements

BIN_OPS is worth a look, because it is a trick you will reuse constantly. It maps node types to the functions that implement them.

server.pylines 29–41
BIN_OPS = {
    ast.Add: operator.add,
    ast.Sub: operator.sub,
    ast.Mult: operator.mul,
    ast.Div: operator.truediv,
    ast.FloorDiv: operator.floordiv,
    ast.Mod: operator.mod,
    ast.Pow: operator.pow,
}

UNARY_OPS = {ast.UAdd: operator.pos, ast.USub: operator.neg}
CONSTANTS = {"pi": math.pi, "e": math.e, "tau": math.tau}

Functions in Python are ordinary values: you can store one in a dictionary and call it later. So instead of seven if branches, there is one lookup. Supporting a new operator becomes a one-line change to a table, and — crucially — the table doubles as the security policy.

BIN_OPS.get(type(node.op)) returns None for anything not listed, and None raises. That is a whitelist: allowed things are named explicitly, and everything else is refused by default. The opposite approach — blocking known-bad input — is a blacklist, and it fails the moment someone thinks of something you did not.

Try it. Send __import__("os") to this server and it reaches the ast.Call branch, finds __import__ is not in the functions dictionary, and answers {"error": "Unknown function"}. Not because anyone thought to block it, but because nobody ever allowed it.

Guarding the resources

A valid, permitted expression can still be a weapon. 9 ** 9 ** 9 uses only whitelisted operators and would occupy the server for a very long time. Three constants near the top of the file cap that.

server.pylines 93–97
MAX_EXPONENT = 1000          # keeps 9 ** 9 ** 9 from hanging the server
MAX_EXPRESSION_LENGTH = 200
MAX_FACTORIAL = 500          # 500! is already a 1135-digit number

Errors as a design decision

The file defines one exception of its own, on line 25, with a one-line docstring that carries the entire rule:

server.pylines 25–26
class CalculationError(Exception):
    """Raised for anything the user can fix by editing their expression."""

That sentence draws a line. Divide by zero, an unknown function, a bad exponent — all CalculationError, all caught in one place and returned as a 400 with a readable message. Anything not a CalculationError is a bug in the server, and is allowed to crash loudly rather than be dressed up as user error. Being deliberate about which failures are expected is most of what separates code that is pleasant to debug from code that is not.

The server is stateless. It keeps nothing between requests — no memory of your last sum, no idea who you are. Every request carries everything needed to answer it. That is why Ans is substituted into the expression in the browser before sending (app.jsx line 350): two people using the calculator at once cannot tread on each other's answer, because there is no shared answer to tread on.

Programmer mode: bases and bits

Why −1 shows as FFFFFFFF, and how the code makes that happen

A base is just how many digits you count with before rolling over. Base 10 uses ten (0–9). Base 2, binary, uses two, so counting goes 0, 1, 10, 11, 100. Base 16, hexadecimal, needs sixteen digits, so it borrows letters: after 9 comes A, B, C, D, E, F. The number does not change — 255, FF and 11111111 are the same quantity written three ways.

Programmer mode has to solve a problem the other modes do not: Python's parser only reads decimal. FF + 1 is a syntax error. The fix is a rewrite pass that runs before parsing.

server.pylines 233, 257–272
TOKEN_RE = re.compile(r"[0-9A-Za-z_]+")   # a run of letters/digits = one number

def _rewrite_literals(expression, radix):
    digits = BASE_DIGITS[radix]

    def replace(match):
        token = match.group(0)
        if any(ch not in digits for ch in token.lower()):
            raise CalculationError(f"'{token}' is not a base-{radix} number")
        return str(int(token, radix))     # "FF" with radix 16 → "255"

    return TOKEN_RE.sub(replace, expression)   # "FF + 1" → "255 + 1"

re is regular expressions — a small language for describing text patterns. [0-9A-Za-z_]+ means "one or more characters from this set". .sub() finds every match and replaces it with whatever the replace function returns. By the time ast.parse sees the string, it is ordinary decimal, and the rest of the evaluator needs no idea that hexadecimal exists.

Note also int(token, radix): converting text to a number in a given base is a built-in, and reaching for the standard library first is nearly always right.

Two's complementhow a fixed number of bits represents a negative number

A real 32-bit register holds exactly 32 bits. There is no separate slot for a minus sign, so hardware uses a convention: the top bit means the value is negative, and a negative number is stored as its positive counterpart subtracted from the wrap-around point.

server.pylines 236–241 · four lines that implement the whole convention
def _wrap(value, width):
    """Truncate to `width` bits and read the result back as signed."""
    value &= (1 << width) - 1          # keep only the low `width` bits
    if value >= 1 << (width - 1):      # top bit set?
        value -= 1 << width            # then it's negative
    return value

1 << width is a bit shift: slide the number 1 left by that many places. At width 8 that is 100000000 in binary — 256. Subtract one and you get 11111111, a mask of eight 1s. & is bitwise AND, which keeps a bit only where both sides have it, so value &= mask discards everything above the eighth bit. Shifting and masking is how nearly all bit manipulation is written, in every language.

_wrap is called on the result of every operation in _eval_int_node, which is exactly what real hardware does — that is what makes the mode a faithful simulation of fixed-width arithmetic rather than just a base converter.

The frontend does the same conversion independently, so the four-base readout can update as you type without a server round trip. It uses BigInt — note the n suffix on 1n and 256n — because ordinary JavaScript numbers lose precision past 53 bits and would silently corrupt 64-bit values.

static/app.jsxlines 300–310 · the same idea in JavaScript
function basesOf(value, width) {
  const span = 1n << BigInt(width);
  const bits = ((value % span) + span) % span;      // always land in 0…span-1
  const signed = bits >= span / 2n ? bits - span : bits;
  return {
    hex: bits.toString(16).toUpperCase(),
    dec: signed.toString(10),                       // only this one is signed
    oct: bits.toString(8),
    bin: bits.toString(2),
  };
}
Two implementations of one rule. This is a real trade-off, honestly made. The duplication buys an instant readout as you type; the cost is that if the convention ever changes, two files have to change together. Recognising that cost — rather than pretending it isn't there — is the skill.

Look and feel: one set of colours

Four themes, 1,079 lines of CSS, and no colour written twice

CSS is the language that says how things look. Its central mechanic is the selector: name some elements, then set properties on them. The naïve way to build four themes is to write the whole stylesheet four times. This file writes it once.

The tool is a custom property — a variable you define with --name and read with var(--name). Every theme is a block that redefines the same twenty names.

The [data-theme="…"] selector matches on an attribute, which is the same mechanism that makes the 3D toggle work: [data-depth="on"] adds perspective transforms to three panels, and switching the attribute off removes them all at once.

A media query asks the browser a question about the current conditions and only applies its rules if the answer is yes. Most are about width — @media (max-width: 720px) is how the layout rearranges on a phone. But prefers-reduced-motion asks about a person: some users get motion sickness from animation and have said so in their operating system settings. Honouring that takes four lines.

The flash-of-wrong-theme problem

There is a subtle ordering bug lurking here, and index.html solves it in a way worth understanding. React cannot apply the saved theme until React has loaded, which is after the browser has already painted the page. A user who chose the light theme would see a flash of dark first.

So a tiny script runs before the stylesheet is even linked — the only JavaScript in the whole project that is not part of the app:

static/index.htmllines 7–29, abridged · runs before first paint
(function () {
  try {
    var saved = localStorage.getItem("calculator-theme");
    if (saved) {
      document.documentElement.setAttribute("data-theme", saved);
      return;
    }
  } catch (e) {}
  try {
    if (window.matchMedia("(prefers-color-scheme: light)").matches) {
      document.documentElement.setAttribute("data-theme", "light");
    }
  } catch (e) {}
})();

Browsers execute scripts in the order they appear, and pause rendering while they do. Putting this one first means the attribute is set before a single pixel is drawn. The fallback chain is the polite one: your saved choice, then your operating system's preference, then the default.

What the app remembers

Three kinds of memory, with three different lifespans

Working out where a piece of information lives, and how long it survives, is one of the real design questions in any program. This one has three answers.

React state lasts until you refresh. The current expression, the history list, whether a request is in flight — all gone on reload, and that is correct. Nobody wants yesterday's half-typed sum.

localStorage lasts until you clear your browser. It is a small store of text, per website, and the app keeps six keys there: theme, 3D on or off, mode, angle unit, base, word size. Preferences, not data.

The server remembers nothing at all. Deliberately.

Every single read from localStorage in this codebase is wrapped in try/catch, and the reason is not paranoia:

static/app.jsxlines 42–56
function readStoredTheme() {
  // localStorage throws outright in some privacy modes, so never trust it.
  try {
    const saved = localStorage.getItem(STORAGE_KEY);
    if (THEMES.some((theme) => theme.id === saved)) return saved;
  } catch (err) {
    /* fall through to the system preference */
  }
  try {
    if (window.matchMedia("(prefers-color-scheme: light)").matches) return "light";
  } catch (err) {
    /* fall through to the default */
  }
  return "dark";
}

In some privacy settings, merely touching localStorage throws an error. Unguarded, that error would happen during the very first render and the page would show nothing at all. A blank screen because someone has strict cookie settings is a bad outcome for a preference nobody would miss.

The second check is just as important: THEMES.some(...) verifies the stored value is one of the four real themes. Stored data is untrusted input — it could be left over from an older version, or edited by hand. Validating on the way in costs one line.

Notice the shape of the function, too. Try the best source, fall back, fall back again, and always return something. It cannot fail. Functions with no failure mode are much easier to build on than functions that might.

Why a server at all?

The general rule, past this app and into every other one

Everything so far has described how this app is split. The harder question is why anything should be split at all — why not do all of it in app.jsx and be done? The answer has almost nothing to do with calculators, and it starts from one fact.

The client is not yours. It runs on a stranger's machine, under their control. They can read every line of it, change any part of it, and lie to you about anything it says.

A web page is code you sent someone. They can open developer tools, edit a variable mid-flight, replay a request with different numbers, or skip your code entirely and call your server by hand with curl. Nothing written on the client is enforcement. It is a suggestion, politely followed by everyone who has no reason not to.

Draw the line where the machines change hands and the whole subject reorganises itself around it.

1 · Trustthe client can lie, and eventually will

Imagine a shop whose checkout page sends the server {item: "laptop", price: 1299}. Nothing stops a buyer editing that number to 1 before it leaves their browser. If the server charges what it was told, it just sold a laptop for a pound.

The fix is not to hide the field, obfuscate the code, or check the price in JavaScript first. It is to stop asking the client for the price at all.

The same shape recurs everywhere. A game that submits its own score. A request that says isAdmin: true. A form claiming its own discount code was valid. In each case the client has been handed a decision that was never theirs to make.

Client-side validation is still worth writing — it tells someone their email is malformed without a round trip, and that is a real kindness. But it is user experience, not enforcement. You need both, for different reasons, and the classic beginner's mistake is building only the first.

The tell: a greyed-out button stops nobody. The request behind it can always be sent by hand.

2 · Secretsanything you ship is public

Every byte sent to a browser can be read. There is no hiding place — not minification, not obfuscation, and emphatically not an environment variable, which frontend build tools paste directly into the bundle they ship. This is one of the most common ways real credentials leak into the world.

So any operation that requires a secret has to happen where the secret lives. You cannot connect a browser straight to a database, because there is no password you could safely give it. Part of what a server is, is the thing that holds the keys and does the privileged work on the client's behalf.

3 · Sharingclients are islands, and someone has to referee

Two browsers cannot see each other. There is no mechanism by which the memory of one tab reaches another. So anything more than one person or one device must see needs a common place to meet: chat messages, a comment thread, a leaderboard, a document two people edit at once, a history that follows you from laptop to phone.

And it is not only storage — it is arbitration. When two people book seat 14A in the same instant, something has to decide who got it. That requires a single point of authority. It cannot be settled between two clients that cannot even perceive one another.

4 · Durabilityclient storage is a promise, not a guarantee

As chapter 07 showed, this app keeps its preferences in localStorage. That store vanishes when someone clears their browser, opens a private window, exceeds a quota, switches device, or loses the laptop. Losing a theme choice is nothing. Losing two years of someone's writing is not. If the data mattering means you cannot lose it, it cannot live only on the client.

5 · Capabilitysome things a browser simply cannot do

Send an email. Charge a card. Reach a printer, or another machine on a private network. Run work too heavy for a phone. Search two hundred gigabytes of data — you send the query to the data, you do not ship the data to every visitor. Browsers are also deliberately sandboxed: no raw sockets, no filesystem, cross-origin requests blocked by default. Sometimes a server exists for no reason other than being a proxy that is not subject to those rules.

6 · You cannot force an updatethe client is always a stale copy

Someone may have a tab open from last Tuesday, or a phone app three versions behind because they never updated it. So anything that must change now, for everybody — a price, a fraud rule, a feature you need to switch off — belongs on the server, where one deploy reaches everyone at once. This is also why APIs need versioning: old clients keep calling you long after you stopped thinking about them.

The other direction

All of which could read as an argument for putting everything on the server. It is not. Some work genuinely belongs on the client, and the industry has moved that way hard.

Anything that must feel instant. No round trip competes with local. Dragging, typing, filtering a list you already hold.

Offline. An app that dies without a network is useless on a plane, in a tunnel, or in a hospital basement.

Privacy as a feature. In end-to-end encrypted messaging the encryption is client-side precisely so the server cannot read it. Sometimes not sending the data is the entire product.

Cost. Work done on the user's processor is free to you, and scales to as many users as you have without you doing anything.

The mature pattern is doing the same thing in both places, for different reasons: validate on the client for speed and on the server for truth; update the screen optimistically, then reconcile with what the server says actually happened.

The decision, in six questions

For each piece of work in an application, ask in order. The first "yes" settles it.

  1. Does it need a secret?server
  2. Does anyone else need to see the result?server
  3. Does it matter if the user lies about it?server
  4. Must it survive this device?server
  5. Is it something a browser physically cannot do?server
  6. None of the above?client

Prefer the client when you can, because it is faster and costs you nothing. Most real applications answer yes to at least one of the first five, which is why most real applications have a server.

And this one? It answers no to all five. No secrets, nothing shared, nothing at stake if you lie about your own arithmetic, nothing worth surviving the device, and nothing a browser could not compute. The Python half is here because the project is a Python project — which is an entirely good reason for something you are building to learn, and not one you could give a client.

The frame worth keeping: the server is not where the work happens. It is where the truth lives. The client is a fast, convenient, completely untrustworthy view of that truth. Which is also why "serverless" is a misleading name — the server is still there; you are renting it by the request instead of running it yourself.

Vocabulary

The words that appear in every codebase, not just this one

API
The set of requests a program agrees to answer. Here: POST /api/calc and GET /api/fact.
Argument
A value you hand to a function when calling it. The named slots it arrives in are parameters.
Array / list
An ordered collection. [1, 2, 3]. Called a list in Python.
AST
Abstract syntax tree — source text rearranged into a structure that makes its meaning explicit.
Async
Work that starts now and finishes later without blocking everything else.
CDN
Content delivery network. A public host for common files; this project loads React from one instead of installing it.
Client / server
The one that asks, and the one that waits and answers.
Component
In React, a function returning a piece of interface.
Dependency
Someone else's code your project needs. This one has two.
Dictionary / object
A collection of named values. {"pi": 3.14159}.
Endpoint
One specific path a server answers on.
Framework
A library that supplies the shape of a program, not just tools for it. Express is one.
Hook
A React function starting with use that gives a component memory or side effects.
HTTP
The request-and-answer format the web runs on.
JSON
A text format for values that every language can read and write.
Parse
Read text and build a structure from it.
Port
A numbered door on a machine, so several servers can share one address.
Props
Values passed from a parent component into a child. Read-only, one direction.
Recursion
A function calling itself on a smaller version of the problem.
Regular expression
A compact pattern for finding or replacing text.
State
The facts a component remembers between renders; changing it redraws the screen.
Stateless
Keeping nothing between requests. Each one carries everything needed to answer it.
String
Text. "7*8" is a string; 56 is a number.
Whitelist
Naming what is allowed and refusing everything else — the safe direction.

Five things to try

Reading code teaches less than poking it

  1. Talk to the server without the browser

    This is the same request the calculator makes when you press =. If it works here, the Python half is fine and any bug is in the frontend — which is how you narrow down a problem.

    curl -X POST http://127.0.0.1:8000/api/calc \
  -H 'Content-Type: application/json' \
  -d '{"expression": "2 + 3 * 4"}'

  2. Watch the whitelist refuse something

    Send an expression that would be catastrophic under eval. You get a polite 400 instead, because the walker never allowed it.

    curl -X POST http://127.0.0.1:8000/api/calc \
  -H 'Content-Type: application/json' \
  -d '{"expression": "__import__(\"os\")"}'
# {"error": "Unknown function"}

  3. Add a key to the keypad

    Add one object to STANDARD_KEYS in static/app.jsx and refresh. No build, no restart — Babel recompiles in the browser. Then find where that key is drawn, and notice you never had to touch it.

    { label: "τ", type: "fn", insert: "tau", aria: "Tau" },

  4. Break the connection on purpose

    Stop the Node service and refresh the page. The calculator keeps working; only the facts bubble changes, to the message written for exactly this case at app.jsx line 613. That is what "handles failure" looks like in practice.

  5. Watch the traffic

    Open your browser's developer tools (F12), choose the Network tab, and press =. You will see the request, its JSON body, the status code, and the reply — the whole of Figure 2, live.
